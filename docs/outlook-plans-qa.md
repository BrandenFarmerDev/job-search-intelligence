# Independent QA: Outlook plans

**Verdict: ready for plan approval, with implementation and mailbox acceptance still gated.** Reviewed [mailbox cleanup](outlook-mailbox-cleanup-plan.md), [collection and upload](outlook-export-process-plan.md), and the existing PowerShell/Worker identity, import, lease and Workflow paths. This is a plan review; no mailbox, cloud, installed task, or implementation was accessed or changed.

The plans now close the material sequencing and scope gaps found during review:

- Collection keeps default Inbox and Sent Items direct-only, recursing only through the newly approved Job Search subtree; existing custom folders need explicit inventory approval. Junk stays outside routine collection, with only manifest-selected job evidence eligible for one-time capture before rescue or cleanup. This aligns the cleanup scope with future evidence coverage.
- Empty destination folders are created as an approved, logged non-mail stage before collector coverage is verified. The later item-level manifest still requires approval for its exact move/delete actions. A naming collision or changed root pauses for clarification.
- Folder paths stay private and the Worker receives only its existing semantic `inbox`/`sentitems` values. Per-item direction must be evidenced; the current import contract rejects custom folder names and the classifier treats `sentitems` as sent.
- The offline queue risk is addressed by binding each queue to a server data generation, rotating it atomically on typed deletion, and checking it with every automated import write. Missing or stale generations fail closed; the epoch is not authorization. The plans preserve the existing route boundary and maintenance lease.
- Cleanup coordination now pauses the task before replacing installed copies, uses the existing named mutex and a durable gate to exclude manual runs, and requires read-only D1/terminal Workflow evidence before moves. Controlled acceptance is explicitly a point-in-time observation; future unattended chain completion remains unverified.

These resolutions are requirements, not implementation evidence. Before mailbox mutations, implementation must demonstrate the one-time Junk capture, complete target-folder discovery, physical-item journaling across moves/restores, `.msg` backup reopenability and attachment/state fidelity, safe restart behavior, generation-fenced import/deletion, and protection against stale offline queues. The generation header and all-write atomic guard are new backend work; verify the D1 transaction/failure behavior with concurrent and lost-response cases. Windows PowerShell 5.1 COM behavior and Outlook cache completeness also need real acceptance. The current scheduled script's parse and `-SelfTest` do not establish collector behavior coverage.

The baseline `npm run quality` passed on the current code according to the root task. No new tests were run for this documentation review. The implementation handoff still needs the planned synthetic PowerShell harness and required coverage gates; provider/cache behavior, the private item inventory, backup restore proof, installed rollout, production import, and live acceptance remain unverified.
