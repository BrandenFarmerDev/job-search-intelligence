# Independent QA: Outlook plans

**Planning verdict: approved by the owner on October 11, 2026.** Reviewed [mailbox cleanup](outlook-mailbox-cleanup-plan.md), [collection and upload](outlook-export-process-plan.md), and the existing PowerShell/Worker identity, import, lease and Workflow paths. The original review below was a plan review; subsequent implementation evidence follows it.

The plans now close the material sequencing and scope gaps found during review:

- Collection keeps default Inbox and Sent Items direct-only, recursing only through the newly approved Job Search subtree; existing custom folders need explicit inventory approval. Junk stays outside routine collection, with only manifest-selected job evidence eligible for one-time capture before rescue or cleanup. This aligns the cleanup scope with future evidence coverage.
- Empty destination folders are created as an approved, logged non-mail stage before collector coverage is verified. The later item-level manifest still requires approval for its exact move/delete actions. A naming collision or changed root pauses for clarification.
- Folder paths stay private and the Worker receives only its existing semantic `inbox`/`sentitems` values. Per-item direction must be evidenced; the current import contract rejects custom folder names and the classifier treats `sentitems` as sent.
- The offline queue risk is addressed by binding each queue to a server data generation, rotating it atomically on typed deletion, and checking it with every automated import write. Missing or stale generations fail closed; the epoch is not authorization. The plans preserve the existing route boundary and maintenance lease.
- Cleanup coordination now pauses the task before replacing installed copies, uses the existing named mutex and a durable gate to exclude manual runs, and requires read-only D1/terminal Workflow evidence before moves. Controlled acceptance is explicitly a point-in-time observation; future unattended chain completion remains unverified.

These resolutions are requirements, not implementation evidence. Before mailbox mutations, implementation must demonstrate the one-time Junk capture, complete target-folder discovery, physical-item journaling across moves/restores, `.msg` backup reopenability and attachment/state fidelity, safe restart behavior, generation-fenced import/deletion, and protection against stale offline queues. The generation header and all-write atomic guard are new backend work; verify the D1 transaction/failure behavior with concurrent and lost-response cases. Windows PowerShell 5.1 COM behavior and Outlook cache completeness also need real acceptance. The current scheduled script's parse and `-SelfTest` do not establish collector behavior coverage.

The baseline `npm run quality` passed on the current code according to the root task. No new tests were run for this documentation review. The implementation handoff still needs the planned synthetic PowerShell harness and required coverage gates; provider/cache behavior, the private item inventory, backup restore proof, installed rollout, production import, and live acceptance remain unverified.

Before the exact item-action approval, settle the local queue disk ceiling and review workflow, encrypted backup destination/retention, Deleted Items versus quarantine, and any explicit exceptions to broad non-job deletion. Keep sensitive, unread, flagged, attachment-bearing, and pre-floor deletion intersections visible in the private manifest. Current counts, folder collisions, task triggers and cache state must be rechecked during authorized inventory.

## Implementation review — October 11, 2026

Implementation used GPT-6 Luna medium agents for the durable uploader/runtime/installer and mailbox utility, with root integration and an independent GPT-6 Luna high review. Source changes add the bounded collector, encrypted recoverable queue, shared maintenance gate, generation-fenced import and Workflows, and a private inventory/review/backup/move/recovery utility. Release and exact item-action approval remain separate gates.

Concrete review findings corrected include generation rotation between a Workflow precheck and lock/history creation, generation capture after a pause check, fail-open corrupt maintenance gates, inconsistent cross-tool gate binding, checkpoint/queue commit ordering, backup journal status and evidence loss, interrupted move restart handling, plaintext scratch ACLs, future-dated recovery proofs, and Junk folder direction inferred without recipient evidence. The installer now persists the gate under the mutex before installed-unit mutations. Fault tests and live synthetic restore acceptance are recorded in [QA](qa.md); a passing parse or helper test is not acceptance of those orchestration paths.

A synthetic fidelity test mistakenly passed the shared Windows TEMP folder to an ACL helper. No mail was involved. Root restored inheritance on that exact directory without recursive changes and verified inheritance enabled, zero explicit rules and six inherited rules. Scratch helpers now validate private-run containment before ACL changes, with a negative TEMP-path regression. The first isolated PST attempt also exposed an invalid attachment-position fixture argument; no real mailbox item was involved and no restore proof was accepted from that attempt.

Existing npm suite coverage gates remain unchanged. New PowerShell behavior harnesses run under Windows PowerShell 5.1 and pwsh. Bundled Windows Pester measures command coverage and the quality runner requires at least 85% in each of the five runtime files where that tool is available; four-metric PowerShell code coverage remains unmeasured. The cleanup harness invokes the engine, identity and synthetic restore harnesses transitively, so these run under both engines and contribute to command coverage.

The isolated live PST test has not passed sent/draft-state fidelity after restoration. It produced no accepted restore proof; detached synthetic fixture files also remain locked by Outlook until a graceful restart releases them. Synthetic mocks do not resolve this provider failure. Mailbox cleanup remains blocked. Outlook cache completeness, installed-client/server rollout, production capture, real-message backup fidelity, exact action approval and post-cleanup acceptance must not be inferred from synthetic success. No merge/deployment or real-mail move/delete is authorized by this review.

The real inventory also exposed minutes-long PowerShell canonical hashing, which could expire the five-minute idle proof before action checks. A local native serializer preserves the existing canonical format; both-engine golden/reference parity and mandatory full-size performance fixtures cover its output. The native C# internals are not instrumented by Pester. Full-size fixtures run separately from debugger coverage to avoid redundant breakpoint tracing; the 85% per-file command floor remains unchanged. The regression ceiling is 60 seconds per fixture; sub-second synthetic hashing was an observation, not the required threshold. Independent QA reviewed the serializer and this separation without identifying another concrete source blocker.

Final portability review retained real Windows DPAPI checks and added non-Windows fail-closed checks without skipping a harness. Private review fixtures inject synthetic encryption; path-escape fixtures use platform-native paths. A default cleanup-context regression verifies mailbox-specific protection entropy. The final full local quality gate passed with all five runtime files above the fixed command floor; see [QA results](qa.md). Source review found no remaining concrete blocker, while the failed live restore proof and incomplete inventory evidence continue to block mailbox actions.
