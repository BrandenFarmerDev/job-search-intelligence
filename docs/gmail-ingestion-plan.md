## Approved direction and technical plan

On October 11, the owner approved the six recommendations presented in chat: the `+live-jobs` redirect target, Gmail future sending identity, narrow initial routing, daily then weekly gap review, gap-only historical transfer preserving existing records, and mailbox-wide `gmail.readonly` access with labeled-message application constraints. Actual Google OAuth consent/publishing, private rule configuration, transfer manifests and release/provider acceptance remain pending. The technical design below has independent Sol high planning review; polling frequency and hard caps remain subject to actual free-runtime acceptance.

- The application reads only `branden.farmer.dev@gmail.com`. Live selective server rules deliver relevant incoming mail to Gmail; no COM, Graph, IMAP or second application mailbox reader is introduced. Graph and AI remain disabled.
- Preserve all existing D1 records and owner decisions. Default historical scope is existing retained evidence plus audited missing messages since **2026-09-30T07:00:00Z**. Historical transfer is a separately approved operation, not a prerequisite to erasing or rebuilding anything.
- Use personal, external OAuth and `gmail.readonly`, offline access and a protected backend refresh token. Gmail labels/filters are native owner configuration. The application never sends, modifies labels, trashes or deletes Gmail messages.
- Poll bounded Gmail message listings initially. Propose hourly polling only after acceptance; use durable fixed UTC windows, overlapping replay and a weekly from-floor reconciliation. Do not add Pub/Sub, push subscriptions or a billing account.
- Use the exact `Job search` label as explicit inclusion. Parent labels are not implied by child names. Labels guide organization; backend evidence determines application events. Alert-only mail is retained in Gmail and excluded from application creation; conflicting or uncertain job evidence enters Review.
- Use Gmail as the future sending identity and manually label each relevant sent message. Incoming redirect does not capture Live Sent Items; the app must disclose this coverage limit.

The owner settled the routing, sending, review, historical-scope and OAuth-access choices above. The exact historical transfer tool/manifest and actual project's OAuth publishing/exemption path still need their documented evidence. This approval does not authorize merge, deployment, schedule activation, wider scopes or mailbox cleanup.

## Personal OAuth and private account binding

Create separate test/production OAuth projects/clients and synthetic test mailbox; do not grant preview access to the real Gmail or tracker. The existing Sheets service account has no personal Gmail delegation: preserve its secret and grant. Personal Gmail is not a Workspace domain-wide delegation account. Use Google's web-server authorization-code flow with offline access, PKCE, a one-use expiring state, owner principal, environment/provider binding and secure HTTP-only callback cookie. Register exact HTTPS API callback URLs; a login hint is a convenience, never authorization. [Web-server OAuth](https://developers.google.com/identity/protocols/oauth2/web-server), [service-account delegation](https://developers.google.com/identity/protocols/oauth2/service-account).

After exchange, call Gmail `users.getProfile(me)` and require the normalized returned address to equal the configured ingestion address. Bind the connection and encrypted refresh token to provider, mailbox, environment and connection generation; reject wrong accounts before storing tokens or resuming imports. Access `OWNER_EMAIL` and policies remain Live-based unless the owner separately requests an access change. Require the existing owner session at callback, enforce state-cookie equality and consume state once. Add OAuth provider/environment, explicit owner intent (`connect` or separately requested `connect_and_resume`) and the starting dataset/connection generation to state storage so Microsoft and Google states cannot be confused and a callback begun before deletion/disconnect cannot reconnect afterward. The existing mutation wrapper recognizes only Microsoft's GET callback: Gmail's exact callback path must explicitly take the same maintenance lease and perform atomic generation checks. Permit its cross-site GET without an Origin only through owner authorization/state/cookie validation; do not broaden mutation Origin exemptions. Connecting and explicitly resuming imports are separate owner actions. Redact authorization codes/state and provider response errors from callback URLs, response bodies and diagnostics; redirect to a fixed frontend URL with only safe status codes.

Request only `https://www.googleapis.com/auth/gmail.readonly`; inspect granted scopes and fail closed on missing read access or unexpected send/write/delete scopes. Never combine with existing broader grants through automatic incremental consent. Client secret is a Worker secret; refresh token is AES-GCM encrypted in D1 under the existing per-environment encryption key. Access tokens remain transient and are reacquired inside private steps. Do not put credentials, OAuth codes, cookies, real headers/bodies or provider error bodies into logs, Workflow outputs, frontend, Git or test reports. Existing minimal excerpt retention remains 30 days; disconnect retains evidence and clears Gmail credentials/checkpoints without affecting Sheets.

`gmail.readonly` is a **restricted** scope and is mailbox-wide: labels constrain app behavior, not the grant. Google's general rule requires restricted-scope review and assessment for server handling, while its personal-use guidance permits fewer-than-100-user personal applications without verification. Record the actual project's eligibility and consent configuration; do not assume a private Access site automatically supplies an exemption. If Google requires a paid assessment or configuration incompatible with $0, stop unattended acceptance and return the concrete decision. [Gmail scope rules](https://developers.google.com/workspace/gmail/api/auth/scopes), [personal-use exceptions](https://support.google.com/cloud/answer/13464323), [assessment process](https://support.google.com/cloud/answer/13465431).

An external app left in Testing gets Gmail refresh tokens lasting seven days. Production acceptance therefore requires an appropriate **In Production** publishing status and recorded verification/exemption basis, followed by fresh consent where needed. This removes the Testing-specific seven-day condition, not all expiration: revocation/password changes can invalidate refresh tokens. Show `reconnect_required`, pause Gmail reads and preserve checkpoints on `invalid_grant`; do not silently switch providers. Prove refresh after access-token expiration and across an observation beyond seven days before accepting an ongoing schedule. With scheduling disabled, perform owner-authorized bounded manual refresh checks on dated days, including after day seven; a separate observation automation would itself need explicit authorization. No continuous operation is claimed from those manual checks. [Refresh-token lifetime](https://developers.google.com/identity/protocols/oauth2#expiration).

## Inclusion, time and MIME evidence

Resolve exact label IDs from native owner-created labels: `Job search` plus Application receipts, Recruiter follow ups, Interviews, Offers, Rejections, Job alerts and Review children from the routing plan. Missing/renamed root label fails closed with a setup status; never replace it with a whole-mailbox search. Every candidate, including Sent, requires the root label. Child labels, Gmail thread membership and plus-address headers do not independently authorize ingestion. Fetch by **message**, not entire thread, to avoid reading an unrelated message sharing a conversation. Root-labeled alert-only mail is acknowledged without application/event creation. Alerts plus lifecycle evidence, conflicting lifecycle categories, ambiguous employer/role or identity collisions require Review; no blanket `-label:Job alerts` query may hide those conflicts.

Use `users.messages.list` with the root ID, `maxResults=20`, explicit pagination, query exclusions for Trash/Drafts and `includeSpamTrash=true`; include root-labeled Spam with a visible source warning. Validate current root/system/category labels through a metadata fetch before requesting a new body, and recheck returned full-message labels before storing/processing it. A concurrent label change cannot retroactively undo an authorized in-flight fetch, but must prevent persisted unrelated evidence. The owner must still inspect unlabelled Spam/Junk: the reader cannot discover excluded personal mail. Gmail applies all listed label IDs as AND, so do not pass all category IDs expecting OR. List results contain IDs/thread IDs, not bodies; list estimates are not completeness evidence. [Message listing](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/list).

Pass UTC epoch seconds in search queries and deliberately overlap one second at window boundaries; enforce the exact floor after fetch. Gmail's date-only search has timezone behavior, and UI thread/alias searches differ from the API. [Search semantics](https://developers.google.com/workspace/gmail/api/guides/filtering). Store separately Gmail `internalDate` (receipt/discovery ordering), original header date and chosen event time. Newly redirected or migrated old mail can have a recent internal date. Ordinary direct mail uses valid internal receipt/sent semantics; redirected/historical mail needs accepted original-date provenance. If original event time cannot be established or conflicts materially, quarantine for review rather than inventing an application date or silently importing pre-floor events. Older mail stays in Gmail and existing D1.

For new accepted candidates request `format=full` with limited fields. Parse MIME recursively with bounded base64url decoding, charset handling, depth/part count and total decoded bytes. Prefer plain text; use the existing bounded HTML text parser without remote content, scripts or image fetching. Keep at most the existing 1,500-character useful evidence excerpt; retain no raw MIME. Proposed safety ceilings: 1 MiB response, 100 MIME parts, depth 20, 64 KiB selected text and 6,000 characters for local extraction. Bounds/unsupported charset/encrypted or attachment-only evidence become explicit Review/unsupported states, not successful empty evidence. Carry root-label candidacy and forced-Review reasons into the adapter: current `classify()` can return no type and `processMessages()` then creates no Review record. A vague recruiter message such as “Tuesday works,” explicit Review label or unsupported evidence must produce a durable app Review item even without job keywords, without inventing an event or application.

Attachments remain in Gmail; store only minimal filename/type/size metadata when required for a coverage warning. Do not download binary attachments or parse PDF/DOCX/ICS in this phase. A text body delivered through Gmail's external `attachmentId` needs a bounded text-part fetch; reserve its cost before calling. Do not mistake all external parts for binary attachments. Provider acceptance must verify attachment preservation and access in Gmail; it does not establish attachment content extraction. [Message/MIME resource](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages).

## Durable polling and replay

1. Owner connect/manual sync and later the accepted cron enqueue the current dataset epoch and Gmail connection generation. Recheck both before lease acquisition and after every durable step replay. A reconnect must not unpause typed deletion or Sheets implicitly; only an explicit owner resume does that.
2. Keep a root-label/configuration version and fixed UTC `[start,end)` window in D1. Initial baseline walks day-sized windows from the floor to a captured end time. Resume the same query/page token after interruption; expired tokens restart that window with identity deduplication. Never treat listing as a stable mailbox snapshot.
3. Commit each discovered page's durable candidate work and next page checkpoint atomically under the lease/epoch fence. Discovery is its own instance/phase, isolated from body fetching/classification; `maxResults=20` is a listing envelope, not twenty SQL writes plus processing promised in one instance. Preflight the full atomic page transaction, including individual SQL statements and control reserve; reduce the requested page size before listing if needed. Candidate statuses distinguish pending metadata/body, imported, alert-only, excluded, Review and retryable error. A failed fetch is not skipped by an advanced cursor. Drain candidates separately; a crash after canonical commit before acknowledgement is an idempotent replay.
4. Once caught up, each hourly poll repeats the last seven receipt days through a fixed recent end time, skipping full fetches for known immutable IDs. Revalidate known metadata on reconciliation, not on every recent poll. Reserve daily call/work shares for recent ingestion (60%), oldest-first weekly from-floor sweep (20%) and metadata/controlled recovery (20%); unused shares may be borrowed within the hard cap, but no phase can starve another indefinitely. Older newly labeled/migrated mail and label changes are discovered by the sweep. Show separate recent polling and reconciliation completion timestamps. A very large baseline/sweep resumes across triggers; it never claims complete because a cap was hit. Suggested operator alert: seven-day sweep age or 24-hour recent backlog. Actual volume may require a lower accepted polling cadence or narrower day windows within the same caps.
5. Run a separate **D1-led metadata sweep** over already-known Gmail instances with a durable provider-ID cursor, bounded pages and its own completion timestamp. Root-label listings cannot reveal a removed root label or a message newly in excluded Trash. This sweep fetches metadata for those known IDs, captures removal/Trash/Spam/404 and never fetches their unrelated bodies. Avoid fetching unchanged full bodies. Removing labels, trashing or losing a message affects only its provider-instance availability; canonical availability aggregates retained legacy/other instances rather than overwriting them. Never cascade-delete canonical evidence/events/owner decisions because a listing omits a message; only explicit typed app deletion removes app data.
6. Gmail failure does not enable Live/Graph/local ingestion. Report per-provider Gmail/Sheets results; a partial Gmail run cannot advance overall last-successful-sync. Allow explicitly bounded independent Sheets work if safe, retaining its existing pause setting.

Existing continuations skip mail ingest entirely. Add an explicit, generation-bound phase (`gmail_discovery`, `gmail_candidates`, `gmail_metadata_sweep`, `classification`, `sheets`, `finish`) and durable work reference so an unfinished Gmail page/candidate crawl actually resumes. A generic classification continuation must not mark unfinished discovery complete. Hand-off failure leaves D1 work recoverable by the next accepted trigger; reserve its control-call cost before releasing the lease.

This starts without history cursors: Gmail history can expire and return 404, and polling scoped message listings avoids persisting unrelated mailbox history metadata. If incremental history is later justified, implement full-baseline recovery with the same window/identity fences rather than assuming IDs are timestamps or continuous. [Gmail synchronization](https://developers.google.com/workspace/gmail/api/guides/sync).

## Additive identity and schema design

Add an additive migration after 0004; never truncate, rekey existing canonical records or rebuild application/event tables. Proposed tables: provider message instances keyed by `(provider, mailbox, immutable_message_id)` with canonical reference, namespaced thread, label/status metadata, internal/original dates and evidence digest; Gmail discovery/work items and checkpoint/config versions; identity-conflict review records; durable budget reservations. Extend OAuth state with provider/environment and connection metadata/status/generation. Keep existing canonical IDs, source references, overrides, exclusions and event uniqueness.

Extend typed app deletion to remove new provider instances, candidate/review payloads, Gmail credentials/checkpoints and OAuth states under its existing lease, rotate the dataset generation and retain durable pause. Keep only non-content budget/cooldown counters needed to enforce daily caps; reconnect, disconnect, deletion and a fresh Workflow must not reset the day's spent quota. Secret revocation remains a separately inventoried provider operation, and Sheets service-account secrets are not accidentally removed.

For a new Gmail ID, first use an exact normalized Internet Message-ID match to existing evidence, **then validate compatible sender/subject/date/content evidence before aliasing**. Duplicate or reused IDs with conflicting evidence are quarantined. The current normalization lowercases the entire header and the fallback hashes subject/time/conversation-or-sender; preserve legacy IDs but do not infer safe cross-provider identity from those hashes alone. Gmail thread and Outlook conversation IDs are not interchangeable. Forwarded wrapper Message-IDs, changed subjects/times, absent IDs, and identical newsletter repeats require explicit review. Store a separate provider instance while retaining the original Outlook evidence. An accepted alias must not duplicate classification/events or replace a prior decision; owner-approved richer evidence can be separately versioned/reprocessed.

Synthetic migration fixtures must preserve full snapshots of all legacy tables/keys/relationships/decisions, not just counts, and prove no new application/event on alias replay. A release-time private baseline digest/count comparison excludes only approved new records and schema metadata. Keep private reports outside Git. D1 availability is not proof that all Live history was captured.

## Budgets and bounded recovery

Current Google documentation lists 6,000 units/minute/user/project, 1,200,000/minute/project, list cost 5, get/text attachment cost 20 and an 80,000,000-unit daily billing threshold with later-2026 billing changes. Actual project quotas and billing state must be verified before release; lower quotas win. Proposed **hard application caps**, shared by scheduled/manual/retry/reconciliation work: 500 units/minute, 20,000 units/day, 600 message/text fetch attempts/day, 100 list attempts/day and 24 normal polls/day. Every attempted call, including retry, reserves units atomically first; failed calls do not refund reservations. These are conservative application policy, not provider guarantees. No quota increase or linked billing account is authorized. [Gmail quotas/pricing](https://developers.google.com/workspace/gmail/api/reference/quota).

Use at most two new full-message candidates and one listing page per Workflow instance initially; metadata and full fetches are separate reserved calls. Budget external calls, token refresh, Sheets and D1 together. Persist work and yield before any limit. Retries are at most three per operation, with bounded Retry-After/exponential jitter and a durable cooldown; do not stack nested fetch retries with Workflow retries. Authentication failure gets one fresh-access-token attempt; refresh `invalid_grant` stops. 429/recognized quota 403 and 5xx preserve work and cooldown; permission 403 requires owner action. A message 404 records unavailable evidence without deletion. Oversize/invalid payload enters explicit Review. Daily exhaustion pauses until reset and does not spin continuation instances.

The shared `providerJson()` currently collapses nearly every provider failure into 502 and discards Google reason codes. Add a Gmail/OAuth-specific bounded error adapter that preserves HTTP 401, quota versus permission 403, message 404 and OAuth `invalid_grant` using only allowlisted machine codes from a size-limited response; never expose/log raw provider text. Persist candidate attempt count, stage, `next_attempt_at` and exhausted status separately from provider-wide cooldown/connection status. One poisoned MIME/message item must move to a durable review/failure outcome after its cap while later eligible items continue; a provider-wide auth/quota failure pauses all Gmail work. Queue selection uses due times and bounded age/fairness so a failing earliest message does not occupy every slice.

There is a concrete platform-limit discrepancy to resolve: existing Workflow comments assume 1,000 internal subrequests, while current D1 documentation lists **50 Free queries/invocation** and Workflows lists **50 Free subrequests/instance** and 10 ms CPU. Do not inherit existing 20-by-two classification batches or 15-row Sheets slices without measurement. Enforce an initial envelope of at most 30 ordinary total subrequests plus 10 reserved for heartbeat, retry recovery, failure/finish recording, lease release and hand-off, keeping 10 below the documented ceiling. Reserve each operation's worst-case cost before starting it; if it cannot fit, checkpoint and yield, even below two candidates. Count D1 statements/queries as well as batch calls until actual accounting is demonstrated. Apply this envelope to unchanged classification/Sheets phases too; a single classification or Sheets row per instance is the conservative initial candidate, subject to measured control overhead. Use actual Free preview measurements to choose smaller slices or bulk SQL. If any existing chain cannot fit CPU/query/subrequest limits, a focused bounded-execution correction is an acceptance blocker; a paid upgrade is outside scope. [D1 limits](https://developers.cloudflare.com/d1/platform/limits/), [Workflow limits](https://developers.cloudflare.com/workflows/reference/limits/).

An operation reservation covers the worst case for **one attempt** plus committed failure/finish capacity. Its lifetime retry cap remains durable across Workflow instances. If another attempt cannot fit the remaining instance envelope, record the attempt/error/due time and defer it to a fresh bounded instance or later trigger; do not require the full three-retry classification chain to fit before any first attempt can run, or endlessly yield without progress. Disable broad automatic step retries for stages whose constituent SQL budget cannot be bounded; use explicit durable attempts and idempotent stage checkpoints instead. Only source/work IDs and safe counters leave a step. No fresh instance resets attempts or bypasses daily reservations.

Proposed additional application ceilings are 500 Workflow instances/day, 2,000 Workflow steps/day, 50,000 D1 rows written/day, 1,000,000 rows read/day, and 100 MiB incremental Gmail app storage. Reserve conservative worst-case allowances before work, reconcile D1 row metadata after each batch, and leave headroom for owner dashboard/Sheets/other account use. Caps must include continuations and retries. They require actual usage measurements before activation. Free account quotas are shared; the app cannot alone guarantee account-wide zero charges on a paid account. Verify account plan/remaining free allocations and fail closed if uncertain. Cloudflare's documented Free allowances include 3,000 steps/day and D1 100,000 rows written/day; platform hard failures and application caps both need handling. [Workflow pricing](https://developers.cloudflare.com/workflows/reference/pricing/), [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/).
