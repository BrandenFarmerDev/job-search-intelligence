## Provider and cost findings

- Google explicitly allows personal-use applications with fewer than 100 users to operate without verification, with an unverified-app warning. A production project should be published **In Production**. Record the actual personal-use eligibility, publishing state, requested `gmail.readonly` scope and successful owner consent; Access privacy alone is not an exemption. No paid verification assessment or billing account is assumed. [Google verification exceptions](https://support.google.com/cloud/answer/13464323?hl=en).
- External projects left in Testing receive Gmail refresh tokens expiring after seven days. In Production removes that particular condition; revocation, Gmail-related password changes and other expiration conditions remain. A newly created connection cannot supply the plan's dated refresh observation beyond seven days today. Manual refresh after access-token expiry is useful separate evidence; scheduled-operation acceptance and legacy retirement remain pending the required observation. [Google token expiration](https://developers.google.com/identity/protocols/oauth2#expiration).
- Cloudflare's canonical Workflow limit table lists 50 Free subrequests per instance and 10 ms CPU per step, while the same page's explanatory text distinguishes 50 external and 1,000 internal subrequests. D1's canonical table separately lists 50 Free queries per invocation. Until actual accounting is demonstrated, enforce the approved conservative ceiling of 30 ordinary plus 10 reserved control/recovery operations, counting SQL statements within batches. Do not inherit the old forty-message classification or fifteen-row Sheets envelope. [Workflow limits](https://developers.cloudflare.com/workflows/reference/limits/), [D1 limits](https://developers.cloudflare.com/d1/platform/limits/).
- Free allowances include 3,000 Workflow steps/day, 5 million D1 rows read/day, 100,000 rows written/day and 500 MB per Free D1 database. Quotas are shared with other account usage. Verify the actual plan and usage, preserve application headroom and stop rather than upgrade on exhaustion. [Workflow pricing](https://developers.cloudflare.com/workflows/reference/pricing/), [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/), [D1 limits](https://developers.cloudflare.com/d1/platform/limits/).
- Gmail's documented current new-project quotas are 6,000 units/minute/user/project and 1,200,000/minute/project. Message gets and text attachment gets each cost 20 units; lists cost 5. The documented daily billing threshold is 80 million units/project, with billing changes planned and notice required. Actual project settings and the much lower approved application caps govern acceptance. [Gmail quotas](https://developers.google.com/workspace/gmail/api/reference/quota).

## Acceptance status

Private native-filter source review on October 11 found one root filter and thirteen category/Review filters. Every child repeats the complete grouped candidate predicate; unique-category filters exclude the other five categories, no-category Review excludes all six, and overlap Review covers every multi-category combination. XML properties are limited to search, label and inert size-selector defaults, with no forwarding, archive, deletion, mark-read or Spam-bypass action. The exact private sender criteria and export remain outside Git.

This accepts the generated filter structure only. The owner session must verify persisted native configuration against the reviewed export and prove actual incoming-message behavior with distinct-thread controlled cases (one category, none, two, three and unrelated). Gmail's UI can return entire conversations for a matching message, especially with negative operators; inspect exact message-level labels rather than thread/search counts. Native filters and manual Sent/reply inclusion remain different boundaries. [Gmail search semantics](https://support.google.com/mail/answer/7190?hl=en), [API/UI differences](https://developers.google.com/workspace/gmail/api/guides/filtering).

The execution session subsequently reported fourteen saved native label-only filters, inspected through the Gmail settings DOM. Thirteen exact synthetic messages were delivered in distinct conversations: ten Gmail self-delivery controls and three Live-to-tagged-Gmail deliveries. Five single lifecycle categories and double/triple overlaps received their expected category/Review labels; an unrelated base-address control remained excluded. Gmail API self-delivery omitted the Delivered-To header and therefore did not prove tagged-recipient matching for the unknown/alert controls. The three actual Live-to-tagged-Gmail deliveries supplied that missing boundary: a receipt received root plus receipts, and an unknown conversational message plus an untrusted-sender alert received root plus Review, each with the expected tagged Delivered-To value.

The execution session recorded private before-label evidence, removed the root inclusion label from all thirteen exact fixture IDs, retained them under the separate QA label, read back each message to confirm exclusion, and obtained zero matches for the fixture marker together with the root label. No application sync/connection or production D1 write occurred. This provider result is reported execution evidence; independent QA directly inspected generated filter logic, not the private mailbox contents. These tests do not prove a saved Outlook server redirect rule, closed-PC delivery, MIME/attachment fidelity or complete alert-sender behavior.

## Pre-freeze implementation diagnostics

The following findings were sent to the backend implementer during development. They describe pre-freeze failures, not the final patch. A temporary isolated in-memory D1 probe reproduced the first three failures and was removed immediately after diagnostics; no test or provider data touched production. The final column records the frozen resolution.

| Finding | Concrete failure boundary | Frozen resolution |
| --- | --- | --- |
| New steady-state mail skipped | Recent discovery assigned new IDs to metadata-only sweep; metadata marked them done with a pending instance and no canonical body. | **Resolved:** new IDs enter metadata then body regardless of discovery source; focused regression passed. |
| Full sweep stalls between days | Each completed daily sweep window reset `updated_at`; selection required another seven days when page cursor was null. | **Resolved:** unfinished day windows continue and weekly eligibility uses whole-sweep completion. |
| Source epoch fence is a no-op | Mutating epoch immediately before the candidate/checkpoint batch still committed its writes because stale `INSERT ... SELECT ... WHERE` inserted nothing instead of aborting. | **Resolved:** a constraint-failing sentinel makes every fenced D1 batch atomic on dataset, connection, source, pause and live-lease state. |
| Execution envelope exceeded | Real Workflow plus cold five-ID discovery used 45 SQL statements, four provider fetches and one continuation create: 50 conservative operations with zero retries, excluding any additional recovery work. | **Resolved:** cold setup is split into bounded phases; all-in final measurements are recorded below. |
| Empty pages rejected | An omitted optional `messages` field was treated as invalid rather than an empty Gmail page. | **Resolved:** omission is empty while malformed or oversized arrays fail closed; the real Workflow probe passed. |
| Crawl completion chases current time | Baseline/sweep day advancement repeatedly used fresh `Date.now()` instead of a captured whole-crawl target, allowing ever-smaller unfinished windows. | **Resolved:** baseline and sweep retain fixed durable targets until whole-crawl completion. |
| Review can be swallowed by alerts | Job alerts plus explicit Review with no lifecycle keywords chose alert-only and produced no Review evidence; manual contradictory lifecycle labels were not detected. | **Resolved:** alert-only requires no Review/conflict reason; explicit Review and lifecycle overlap remain durable Review. |
| Partial provider failure can appear successful | Metadata/body 5xx recorded retry work but returned the same false result as an empty queue; later Workflow phases could finish completed with retry backlog. | **Resolved:** retries remain durable by stage, terminal work advances the same phase, and finish rejects any remaining backlog/cooldown. |
| No-event Review acknowledgement incomplete | The no-type Gmail Review branch continued before acknowledging its durable process candidate. | **Resolved:** Review evidence, processed hash and candidate completion commit in one fenced batch. |
| Root listings cannot see removals | Root-only listing sweeps cannot discover removed root labels or newly trashed known IDs. | **Resolved:** the weekly D1-led `known_metadata` cursor reads known IDs independently of Gmail root listings. |
| MIME evidence mismatch | First HTML part could win over later plain text; charset was ignored and external HTML was treated as raw text. | **Resolved:** bounded inline/external MIME projection prefers plain text, parses HTML and rejects unsupported charsets conservatively. |
| Classification and auxiliary writes escape the source fence | Gmail classification updated canonical processing, Review, candidate and instance rows without an atomic dataset/connection/lease predicate. Cold label caching and invalid-page-token checkpoint updates also wrote after only an earlier generation check. | **Resolved:** source/configuration, classification-decision, reconciliation, Sheets and retention writes all use the atomic fence; stale-epoch regression passed. |
| Metadata reconciliation destroys terminal state | An accepted metadata/sweep result rewrote every state except `imported` to `pending` while completing the sweep candidate. Existing Review and alert-only items therefore lost their durable terminal state, and a previously excluded message whose root label was restored became pending/done without body ingestion. | **Resolved:** accepted sweeps preserve imported/Review/alert-only state and restored excluded/unavailable instances return to body ingestion. |
| Known-ID 404 remains falsely available | Terminal 404 handling updated provider-instance availability only for body-stage failures. A D1-led metadata/sweep 404 completed the candidate but left the known instance available. | **Resolved:** metadata/sweep 404 marks the provider instance unavailable and recomputes only Gmail-owned canonical availability without deleting evidence. |
| Alert plus one lifecycle label can be swallowed | Alert-only required no textual keyword but did not treat `Job alerts` plus exactly one lifecycle label as an ambiguity. Neutral text with those two labels became alert-only instead of Review. | **Resolved:** any alert/lifecycle label overlap is a Review conflict independent of keywords. |
| External plain text loses to inline HTML | MIME traversal recorded an external plain part but selected an inline HTML part, and body processing fetched the external part only when no inline text existed. | **Resolved:** external plain text takes precedence; the 27-operation real Workflow regression passed. |
| Cached label IDs are treated as permanent | After cold setup, discovery and status trusted `gmail_label_ids` without re-listing current Gmail labels. Renaming or deleting the root could leave `labels.ready=true` and produce a provider failure from a stale ID instead of a fail-closed setup state; API-side resume did not independently require a complete label configuration. | **Resolved:** every sync starts with bounded label revalidation, stores check time, and reports stale/missing required labels fail closed. |

## Frozen-source verdict

**Pass for the implemented Gmail source and local synthetic evidence, with no open implementation blocker.** Final review covered the refrozen working tree after the backend fixes. The earlier diagnostics above are retained because they identify the actual failure boundaries found during implementation; each was resolved before this verdict.

The independent final probe used the real `JobSyncWorkflow`, the SQLite D1 adapter, real Gmail service functions and fake OAuth/Gmail HTTP responses. It did not mock the Workflow's Gmail phases. Successful invocations recorded these ordinary-operation snapshots:

| Invocation | Ordinary operations | D1 operations | Batch statements | External calls | Result |
| --- | ---: | ---: | ---: | ---: | --- |
| Cold label validation | 19 | 17 | 4 | 2 | Stored the complete current label map and handed off to discovery |
| One-ID baseline discovery | 23 | 21 | 4 | 2 | Atomically stored the candidate and fixed-window checkpoint |

| Body with inline HTML plus external plain text | 27 | 24 | 6 | 3 | Preferred the external plain text, stored its excerpt and handed off the remaining body phase |

The returned snapshots are captured before control cleanup. Source review confirms that each successful continuation then uses four control D1 operations (status replay check, heartbeat, and the two-member finish/release batch) plus one handoff operation. The resulting all-in totals were therefore 24, 28, 26 and 32 respectively, within the fixed 40-operation ceiling and the 30 ordinary/10 control partition. The wrapper reserves all D1 batch members before sending the atomic batch and charges OAuth, Gmail and Workflow handoff attempts. A blocked ordinary operation cannot consume the control reserve.

The focused frozen regression run passed **100 tests in 6 files**: execution-budget, Gmail service, Gmail candidate boundaries, Gmail OAuth boundaries, Workflow and sync. Independent backend typecheck and `git diff --check` passed. The backend refreeze separately reports **188 backend tests** and coverage of **92.74% statements, 85.50% branches, 97.36% functions and 96.31% lines**. Generated Worker types and named preview/production dry-run builds were also reported passing after the configuration changes. After this review and the narrow lint corrections, the frozen full-repository `npm run quality` completed successfully; exact commit, hosted CI/CodeQL and deployed-version checks remain release-stage evidence.

Source and regression review specifically confirmed:

- label validation is its own cold phase; renamed or removed required labels make setup stale or incomplete instead of silently trusting an old ID;
- baseline and sweep windows keep a captured `target_end`, while due recent and historical discovery select the less recently advanced checkpoint so neither starves;
- the D1-led `known_metadata` cursor enumerates known Gmail IDs independently of root-label listings and reconciles removals, Trash and provider 404 without deleting retained canonical evidence;
- permission 403 marks the connection `reconnect_required` without a cooldown or automatic candidate replay; quota failures remain bounded and retryable, candidates keep per-stage attempts, and terminal items advance the backlog;
- every Gmail-derived/configuration mutation, including classification-decision cache writes, Sheets reconciliation and retention, uses the constraint-failing dataset/connection/lease fence; stale-epoch regressions leave both decisions and source rows untouched;
- metadata preserves imported, Review and alert-only terminal state, while a formerly excluded instance restored to eligibility returns to body processing;
- manual Review, alert/lifecycle overlap, multiple lifecycle labels, missing/original-date conflicts and unsupported MIME remain conservative Review cases; external plain text wins over inline HTML, bounded charsets are decoded explicitly, and attachment-only evidence is not invented;
- the explicit finish phase verifies there is no candidate/cooldown backlog before retention and completion; successful prior Sheets work cannot hide an unfinished Gmail queue;
- compatible legacy Message-ID aliases preserve the legacy canonical key and manual reconciliation decisions, while collisions are quarantined and provider removal cannot erase independently retained legacy evidence;
- OAuth uses one-time owner/environment/data-generation/connection-generation state, PKCE, an HttpOnly secure SameSite cookie, an exact `gmail.readonly` grant, mailbox binding, encrypted refresh tokens, manual redirect handling and reconnect-required invalid-grant behavior.

The architecture, README, deployment, QA and release sections now describe the one-day baseline/sweep windows, seven-day recent window, canonical identity behavior, disabled Graph/AI/scheduling state, and the provider work still pending.
