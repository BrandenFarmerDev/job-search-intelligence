# Gmail plans independent review

Reviewed October 11, 2026 by an independent GPT-6.1 Sol high agent. Scope: [routing plan](gmail-routing-plan.md), [ingestion plan](gmail-ingestion-plan.md), repository agreements, current backend/schema at main `bdbfb13`, and current primary provider documentation. No implementation, mailbox operation, deployment or provider acceptance was performed by this review.

## Concrete findings and resolutions

| Finding | Severity | Evidence and failure | Required resolution / review status |
| --- | --- | --- | --- |
| Explicit candidates can disappear from Review | P1 | `services/classification.ts` returns `type:null` for text without job keywords; `services/sync.ts` reconciles only a non-null type. A root/Review-labeled “Tuesday works” or attachment-only candidate could be marked processed without an app Review record. | **Resolved in plan:** carry candidacy/forced-Review reasons into the adapter and create a durable app Review item without fabricating an event/application. Implementation acceptance must exercise this boundary. |
| Copying existing upserts would damage legacy identity | P1 | Migration 0002 has one physical locator per canonical message. Local Outlook conflict updates overwrite evidence; Graph conflict updates also overwrite account/locator. The fallback identity includes provider-specific conversation or sender/time evidence. | **Resolved in plan:** additive provider instances, validated aliases, namespaced conversations and collision review; retain legacy keys/manual decisions and prohibit automatic reprocessing on alias replay. Test full legacy snapshots and relationships, not counts alone. |
| Cached OAuth callback can reconnect deleted data | P1 | Existing OAuth state has no provider/dataset generation; the mutation wrapper recognizes only Microsoft's GET callback. A Google callback copied from the current pattern could bypass the intended maintenance/generation boundary. | **Resolved in plan:** one-use owner/provider/environment/intent/epoch state, exact leased Google callback, atomic generation checks, separate explicit resume and narrow Origin handling. Deletion/disconnect invalidates a prior callback. |
| Legacy continuation cannot resume Gmail discovery | P1 | `workflow.ts` explicitly skips mail ingest in continuation instances. Reusing it for bounded Gmail pages could leave discovery incomplete while classification/Sheets finish. | **Resolved in plan:** explicit generation-bound discovery/candidate/metadata/classification/Sheets phases and durable work references. Failed hand-off leaves recoverable D1 work. |
| Current batch assumptions exceed conservative Free envelopes | P1 | Current Workflow batches classify up to 40 messages and reconcile 15 changed tracker rows. D1 documentation lists 50 Free queries/invocation; Workflows' limit table lists 50 Free subrequests and 10 ms step CPU. Twenty discovery writes plus processing/retries cannot be presumed to fit. Provider pages themselves use differing internal/external subrequest descriptions. | **Resolved in plan:** isolated/adaptive discovery, count SQL statements as well as batch calls, 30 ordinary plus 10 control/recovery envelope and measured smaller classification/Sheets slices. Actual Free account/runtime acceptance remains a release blocker. [D1 limits](https://developers.cloudflare.com/d1/platform/limits/), [Workflow limits](https://developers.cloudflare.com/workflows/reference/limits/). |
| Root-only polling cannot observe root removal | P2 | A root-label query never returns a previously known message whose root label was removed, and Trash exclusion also removes relevant status changes from those listings. | **Resolved in plan:** separate D1-led known-ID metadata sweep with durable cursor/timestamp, without fetching unrelated bodies; availability remains per instance and retained legacy evidence is preserved. |
| Imported Live Sent is not native Gmail Sent | P1 | Gmail reserves system `SENT` semantics; imported messages retain Live From headers, which alone do not prove source direction. Treating them as received changes follow-up classification and event times. | **Resolved in both plans:** separate manifest-bound direction/folder/time provenance tied to Gmail ID and MIME hash; historical Sent ingestion is deferred until that reader contract and real examples pass. No manufactured SENT/From/Date. [Gmail labels](https://developers.google.com/workspace/gmail/api/guides/labels). |
| Narrow routing cannot promise zero unrelated transfer | P2 | An unknown “Hello” recruiter misses lexical rules, while unrelated mail containing an approved interview phrase matches. Incoming filters and prior thread labels also do not automatically cover new Sent/reply messages. | **Resolved in routing plan:** explicit recall/privacy tradeoff, owner gap review, per-message Sent labeling and separate negative versus lexical-collision acceptance cases. No blanket mailbox body search. [Gmail filters](https://support.google.com/mail/answer/6579). |
| Generic HTTP helper erases Gmail recovery semantics | P1 | `services/security.ts:providerJson` maps every non-410 provider failure to 502 and discards structured error reasons. Reusing it unchanged cannot distinguish revoked refresh (`invalid_grant`), authorization/permission/quota 403, message 404 and retryable 5xx as the plan requires. | **Resolved in plan:** bounded Gmail/OAuth-specific adapter preserves status and allowlisted machine codes without raw-body logging. Implementation must prove each required recovery branch. |
| Retry reservation can stall progress or reset forever | P2 | A current multi-query classification multiplied by all retries may exceed the 40-call envelope before starting. Re-selecting the same failing oldest candidate each trigger, or resetting attempts on a new instance, can consume every slot without progress. | **Resolved in plan:** durable per-item attempts/stage/due time/exhaustion and fairness, separate provider cooldown, one-attempt budget reservation and explicit retry deferral across instances. Daily spent counters survive reconnect/deletion. Implementation must prove progress and bounded exhaustion. |

## Verified design constraints

The plans separate mailbox identity from Access owner identity, keep personal Gmail read-only and private backend credentials, preserve unrelated Sheets credentials, prohibit fallback ingestion, and retain the paused Windows task/recovery evidence. Gmail category labels remain advisory; alert-only exclusion must not swallow contradictory application evidence.

The OAuth discussion correctly treats `gmail.readonly` as mailbox-wide restricted access, not label-scoped access. Personal-use verification exceptions and In Production publishing must be resolved for the actual project; private Access does not itself establish an exemption. Testing refresh tokens have a seven-day condition; manual dated refresh observation while scheduling is off is distinct from continuous scheduled-operation acceptance. [Google personal-use guidance](https://support.google.com/cloud/answer/13464323), [refresh expiration](https://developers.google.com/identity/protocols/oauth2#expiration).

Google currently documents January 2027 removal of third-party Send as; the owner has now approved Gmail From as the future identity. Selective redirect behavior, MIME/attachment integrity, Junk coverage and original identity still require controlled live evidence. The separate temporary historical import grant must never become the runtime token or a second application reader. [Google third-party account notice](https://support.google.com/mail/answer/17101213?hl=en), [Microsoft redirect behavior](https://support.microsoft.com/en-us/outlook/mail/use-rules-to-automatically-forward-messages).

## Owner decision update and unresolved acceptance

After this independent review, the owner approved all six chat recommendations on October 11: tagged redirect, Gmail future From, narrow routing, daily then weekly gap review, historical gaps only, and mailbox-wide read-only OAuth constrained in code to labeled job mail. These are recorded in both plans. This update records owner input and does not convert design acceptance into provider or release acceptance.

- Remaining configuration/evidence: exact private rules/exceptions; historical manifest/tool and any Sent provenance scope; actual OAuth publishing/exemption path. Recipient/tag, future sending identity, gap-review duties, gap-only scope and read-only grant boundary are settled.
- Provider evidence: closed-PC redirect, unrelated controls and known lexical collisions, correct per-message labels, Spam/Junk recovery, reply/header/MIME/attachment fidelity, refresh after expiry/day seven, revocation/reconnect and bounded failure recovery.
- Data evidence: read-only baseline/recovery point, additive migration, legacy relationship/decision preservation, duplicate/collision replay and separately authorized synthetic deletion/epoch tests.
- Cost/runtime evidence: actual Google project quotas/billing state and Cloudflare plan/shared allocations; all-in CPU/query/subrequest/retry/step/storage measurements and hard-cap stop behavior. Documentation or mocks do not establish $0 acceptance.
- Release evidence: approved implementation, targeted checks, independent Sol high QA, frozen-source final quality, generated Worker types/named dry runs where applicable, and exact-commit hosted checks. Gmail merge/deployment, scheduling and retirement retain separate gates.

Final re-review found the concrete planning findings above resolved in the documents. The owner subsequently approved the six presented design recommendations; this remains design review acceptance only.
